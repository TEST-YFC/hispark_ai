# 故障排查：错误信息 → 根因

本表用于 workflow 将构建或 Host 失败回流实现 leaf 后定位根因。先保存原始错误，再按表做最小源码修复；修复后
重新执行实现质量门禁并交回 workflow 构建和验证。本 leaf 不直接修改 Host harness，也不自行烧录。

很多算子 bug 在 codegen 时（`session.cc::CreateOpCoders` 跑 ③populate、④infer 再选 ⑥opcoder）才暴露。按日志对照根因；每行的"修复"列指向 `implementation-guide.md` 对应层的细节。

| 现象 / 日志 | 根因 | 修复 |
|---|---|---|
| `InferShape failed, name: <node>`（来自 `session.cc`） | ④ infer 缺失或输出形状算错 | 实现/修正 `nnacl_c/infer/xxx_infer.c`，确认 `REG_INFER` 的 `PrimType_*` 与 parser 一致 |
| `GetParameterCreator` 返回空 / populate 处崩溃 | ③ populate 缺失或 `PrimitiveType` 不匹配 | 补 `xxx_populate.cc`，核对 `REG_POPULATE` 的类型枚举 |
| 找不到 opcoder / `FindOpCoder` 失败 | ⑥ opcoder 未注册，或 `CoderKey(target, data_type, prim)` 不匹配 | 确认 `REG_OPERATOR_CODER` 的 target、data_type、prim_type 三元组 |
| `riscv_quant` 余弦恰好 `1.0000` | ⑦ 算子未加入 `enable_all_ops`，tensor 仍是 fp32，按 `inputs[0]->data_type()` 选中了 fp32 coder | 在 `full_quant_quantizer.cc` 的 `enable_all_ops` 块 emplace 该 primitive |
| `[<op>_int8.cc:NNN] Prepare] <Op> unsupported mode: N` | bias_correction 阶段，多路复用的运行时 int8 kernel 缺对应子类型分支 | 在该 kernel 的 creator / `Prepare()` 补 case（见实现指南 ⑤ int8 kernel） |
| `encounter an unknown error...` + `PreBuild or PreInference failed`（全量化时，fp32/riscv 变体却正常） | 新 fp32 运行时 `KernelBase`（`nnacl_c/kernel/xxx.c` 的 `CreateXxx`）漏设 `base_.Release`，销毁时 `nnacl_kernel.cc` 无条件调 NULL 指针 → pre-inference 子进程段错误 | `CreateXxx` 补 `base_.Release = DefaultRelease;`（四个 vtable 指针设全，见实现指南 ⑤） |
| `can not find MSOpsRegistry for op: <Op>` + `old_nodes is empty` + `UNSUPPORTED OP LIST: <Op>`（但 parser 日志有 `parse op:<Op>`） | 漏了 ①‴：新 PrimitiveType 没注册进 `MSOpsRegistry`，ANF→MetaGraphT 导出时按名查不到 creator，节点被静默丢弃 | 在 `src/common/ops/ops_utils.cc` 加 `REG_MINDSPORE_OPERATOR(<Op>)`（见实现指南 ①‴） |
| **构建**报 `'<Op>T' is not a member of 'mindspore::schema'` / `has no member named 'value_as_<Op>'`，而 ops_def.cc 的 `OP_TYPE/OP_SCHEMA_DEF` 明明已正确添加 | CMake 不追踪 `ops_def.cc → ops.fbs → model_generated.h` 的再生成链，`build/schema/{,inner/}model_generated.h` 是上一轮的陈旧缓存——重跑构建**不会自愈**（实证：烧一整轮构建才定位） | `build_mslite.sh` 已按 mtime 自动删缓存头（ops_def.cc 新于生成头即删）；手工处置 = `rm -f build/schema/model_generated.h build/schema/inner/model_generated.h` 后仍经脚本重跑。预检阶段的同型报错由 `quick_check.sh` 判 `SCHEMA_PENDING`，不阻塞、不要试图在预检层"修复"它 |
| 算子在生成代码里凭空消失（parser 明明跑了） | 激活子类型 parser 返回了独立 op 类，MetaGraph 序列化时静默丢弃；或某融合 pass 重写了子图 | parser 改返回 `ops::Activation`（见实现指南 ②）；或审计 `tools/optimizer/fusion/`（见 decision3 融合判定） |
| hs-verify-op-host 里 MCU 端 `make failed`（但 `converter_lite` 转换成功） | ⑥ opcoder 的 `Collect()` 漏列了生成代码引用的头/源（如 parameter 头），或生成的 C 用了未 Collect 的符号——**宿主侧转换通过 ≠ 目标侧编译通过**，遗漏只在 MCU `make` 暴露 | 看 `benchmark_work/<Op>_*/stderr.log` 找缺失符号/头，在 `Collect()` 补齐生成代码用到的每个 `.h`/`.c`；标量属性按实现指南 ⑥′ 直接传值可免收 parameter 头 |
| hs-verify-op-host 某路径 `error while loading shared libraries` / `c_api/model_c.h: No such file` | `MSLITE_PKG` 指向了原始 `build/` 而非解压包 | 回流 workflow stage2，改指 `output/mindspore-lite-<ver>-linux-x64/`；详见 `<hs-workflow-op-development>/references/build-and-toolchain.md`。 |
| `malloc(): corrupted top size` / `sysmalloc: Assertion failed`，发生在 riscv_int8 全量化（bias_correction）阶段，**大张量崩、小张量侥幸过**，fp32 与 x86 路正常，ASAN 下因分配向上取整反而不崩 | 首输入为 condition/index（bool/int）的算子按 `inputs[0]` 派发选中了 **fp32** kernel，它把 int8 数据缓冲当 `float*` 写（4 字节/元素）→ 堆越界 | 固定键（bool）的 runtime kernel 内部按**数据张量** `in_[1]->data_type_` 分支，int8 走 ⑤‴ 模板**逐输入重量化**；不要给 int8 单独注册 kernel（死代码）。见实现指南 ⑤″/⑤‴ |
| converter **一启动就 SIGSEGV / `SEGV_ACCERR`**，无任何日志，解析模型前就崩，fp32-only 变体同样崩，注释掉 `REG_KERNEL_CREATOR` 就不崩 | 新 `PrimType_Xxx` 放进了 inner 段（10000+）或没把 `PrimType_MAX` +1 → kernel 注册表 `g_kernelCreatorRegistry[PrimType_MAX][16]` 在静态初始化期被越界写穿（`nnacl_c/kernel.c`） | 把 `PrimType_Xxx` 移到 `op_base.h` **标准段**末尾（当前最大值 +1），并 `PrimType_MAX = PrimType_Xxx + 1`（见实现指南 ① 的 ⚠️ 两区段说明） |
| fp32 全过；`riscv_int8` **仅「输出分布≠输入分布」判别用例 FAIL**（cos≈0.9x），其余 int8 用例 ≥0.99 | int8 通路是字节拷贝/漏重量化——输入侧 qparams 被原样带进输出，形成仿射失真；同分布用例因 scale 恰好相近而侥幸通过 | 按实现指南 ⑤‴ 模板逐输入重量化；量化 trait 不构成豁免（int8 约定 §9） |
| `riscv_int8` **恰在输入/输出值域相同的用例上 FAIL**，输出量级约为参考的一半；重量化用了 `QuantizeMultiplierSmallerThanOne`/`MultiplyByQuantizedMultiplier` | 定点乘数接口对 `ratio ≥ 1` 无定义——ratio=1.0 时产出 `mult=0x40000000, shift=0`，效果是除以 2 | 改回 ⑤‴ 模板的 `float ratio + lrintf` 写法（对任意比值正确）；**不要**补"scale 相等时跳过重量化"特判 |
| 编 `coder_mid` 报 `serializer.h: no match for 'operator<<'`，操作数类型是你新建的 `XxxQuantArg` 子结构体 | `CodeBaseStruct` 序列化的结构体里嵌套了子结构体，serializer 缺该子类型的流输出 | 首选把量化参数结构体**扁平化**为标量字段（⑤‴ 的结构性约束）；确需嵌套才在 `nnacl_stream_utils.{h,cc}` 补 `operator<<`（声明/定义/include 三处） |
| 复用分支的新 parser 编译报 `'Xxx' in namespace 'ops' does not name a type` / `is not a member of 'ops'` | 已有算子的 `ops::Xxx` 原型类多在子模块自动生成的 `auto_generate/gen_lite_ops.h` 或 `mindspore/ops/infer/xxx.h`，不在新建分支模板写的本地 `primitive/` | grep 真实定义位置后 include 它，路径写法照抄同目录已有 parser（见实现指南 ② 复用分支小节） |
| 编 `opcoders/base/` 下的新 coder 报 `'NNaclFp32Serializer' was not declared in this scope` | serializer 类在 `mindspore::lite::micro::nnacl`，base/ coder 在 `mindspore::lite::micro`，缺 using 声明（nnacl/ 下的参考算子因同处 nnacl 命名空间而看不到这行） | 文件顶部补 `using mindspore::lite::micro::nnacl::NNaclFp32Serializer;`（int8 同理）（实现指南 ⑥ 目录约定） |
| 同形/标量用例全过，**广播用例** fp32 余弦掉到 0.0x–0.5（甚至越修越差） | 手写广播 stride 错位（`stride[d]=stride[d+1]*shape[d]`，应乘 `shape[d+1]`）；或快路守卫用"任一输入是标量"弱条件放行了仍需广播的输入；或用 `i % num` 近似广播索引（仅最外维广播碰巧正确） | 按实现指南 ⑤⁗ 公式修，或改调既有广播设施（broadcast_to 物化）；快路条件改为对每个输入逐一成立 |
| 给复用算子补 int8 后，**原本正常的 fp32/fp16/广播路径行为异变或新 FAIL**；或新建的 kernel 文件加日志后发现**从未被执行** | 为已由 `NNACL_KERNEL(...)` 承载的算子按同键又注册了 `REG_KERNEL` C++ kernel——creator 注册表优先（`kernel_registry.cc::GetLiteKernel`，命中即不查 nnacl），新 kernel **整体劫持**该算子全部执行，既有 nnacl kernel（广播物化/快路/fp16）沦为死代码；反向注册在 int8 键则因首输入派发永不被选中 | 删除平行 kernel 及其注册；回到既有体系扩展：`XxxStruct` 加扁平 quant 字段 + `kernel/cpu/nnacl/nnacl_xxx.cc` shim 从 `quant_params()` 填充 + 分支加在 `xxx.c`（实现指南 ⑤″ 第 7 条） |
| 某**特殊形态用例**（rank-1 条件、某种广播形态）fp32 FAIL，而运行时 kernel 明明已支持该形态（宿主 benchmark 正常） | ⑥ coder 没有调 kernel 同款 nnacl 函数：形态逻辑是 coder 内联副本（曾在修编译错误时被删/简化），或 nnacl 函数缺形态参数、coder 只发了常规调用 | 形态逻辑下沉到 nnacl_c 函数（扩签名加 mode/stride 参数），⑤/⑥ 调同一函数（实现指南 ⑥「DoCode 只发数据 + 调用」）；对照 decision4 能力验收清单逐条核对 |
| 构建失败，错误摘要只有 `collect2: error: ld returned 1 exit status`，看不到别的 | 链接失败的真正信息（`undefined reference to ...`）**不含 "error:" 字样**，被只 grep "error:" 的摘要漏掉 | 第一动作 = 用本轮 `build_mslite.sh --status "$RUN_ID"` 看「链接失败」专项，或在确认日志头 RUN_ID 一致后检索 `/tmp/mslite_build.log` 定位符号与 target。**拿到符号名之前，禁止清缓存或全量重建碰运气**。 |
| 链接报 **本次新增 `.c/.cc` 的符号** undefined（编译日志里该文件可能已出现 `Building ... .o`） | 该文件没进**失败 target** 的链接闭包：所在目录的 CMake 用**显式源列表**（必须手动添加文件名，GLOB 才自动收）；或目标文件进了库 A、失败 target 链的却是库 B | 读失败 target 对应的 CMakeLists 确认源收集方式；用 `nm <候选 .a> \| grep <符号>` 核实符号归属，再决定补源列表还是调整文件归属。RISC-V ExternalProject 特例按 `<hs-workflow-op-development>/references/build-and-toolchain.md` 分诊。 |

> **opcoder 看到的是序列化后的 `MetaGraphT` flatbuffer，不是活 ANF 图**：没编码成真正 `PrimitiveType` 的东西在 `MetaGraph::Pack` 时即被丢弃，到不了 opcoder。这是"parser 跑了但算子在生成代码里消失"一类现象的总根源。
