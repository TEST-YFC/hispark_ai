# WS63 Optimization Runbook

同时执行上级 `workflow.md`。选择优化方向、诊断瓶颈或判断停止条件时，再完整读取
[ws63-methodology.md](ws63-methodology.md)。

## 固定协议

- codegen target：RISCV；
- 标准 metric：`latency`，单位 `us`，越低越好；
- TCXO 默认 `24.0 ticks/us`，运行前按当前板级时钟配置复核；
- 有效样本：`[AI_MCU][PREDICT] OK seq=<n> ticks=<ticks>`；
- `seq` 必须为正且连续，ticks 必须为正；
- 默认窗口 50，稳定阈值 5%；baseline 与全部轮次的 manifest 必须使用相同参数；
- 板端精度必须先由 `hs-debug-op-board-accuracy` 判定 PASS。

采样结果使用 `format_version=2`，保存 execution ID、完整稳定窗口、时钟换算参数、阈值和超时。
归档器逐项与准备阶段的 manifest 对账，不接受只有平均值的 JSON。

## Package 顺序

修改 NNACL 时：

1. 用 `hs-dev-op-implement` 重建 CPU `libnnacl.a` 并刷新 Host package；
2. 运行完整 Host 精度；
3. 重建 RISC-V `libnnacl.a` 并刷新 target package；
4. 构建 firmware、flash、board accuracy；
5. 采集 latency。

只修改当前 case 的生成 `net0.c` 时，记录原因并保持 MindSpore Lite 源码干净。CPU/RISC-V
archive 始终是必需归档产物；不要把 CPU archive 当成 RISC-V archive，也不要以文件存在代替
架构、新鲜度和 SHA256 对账。

## 计时 firmware

使用 `run_optimization.py prepare` 输出的 execution ID：

```bash
SDK_PATH=/abs/ws63-sdk/src \
python3 <skill>/scripts/build_timed_fwpkg.py \
  --execution-id <EXECUTION_ID> \
  --model /abs/model.onnx --model-name case_name --framework onnx \
  --output-dir /abs/firmware --quantized --calib-dir /abs/input \
  > /abs/firmware_build.log 2>&1
```

包装器在系统临时目录生成 Board builder 副本，在模型输入适配完成后、SDK 编译前注入计时
marker；不修改其他 Skill 文件。它校验 builder 的 `SCRIPT_DIR`、模板恢复和 hook 位置，结构变化
时直接失败。构建日志写入 `HS_PERF_EXECUTION_ID` 和实际 fwpkg 的 SHA256，归档时必须与
manifest 和最终 firmware 一致。

注入器把匹配范围限制在 `ai_mcu_sample_process()` 内，只接受 start tick、Predict、end tick、
Predict 失败检查和 `PostProcess` 的预期顺序；它删除精度不足的毫秒日志，在 Predict 成功后输出
连续 tick marker，并保证重复执行不会重复注入。

使用同一个 execution ID 和刚生成的 firmware 调用 Board flash/accuracy：

```bash
python3 <skill>/scripts/run_board_flash.py \
  --execution-id <EXECUTION_ID> \
  --firmware /abs/firmware/case_name.fwpkg \
  --gt-dir /abs/gt --ctrl-port COM9 --burn-port COM4 --quantized \
  > /abs/flash_board.log 2>&1
```

包装器写入 execution ID 和 firmware SHA256，然后原样委托
`hs-debug-op-board-accuracy/scripts/flash.sh`。归档器要求 build、flash、board 三层记录的 hash 与
最终归档 firmware 完全相同。把这份组合日志分别绑定为 `flash` 和 `board`。

## 采集 latency

先取得 Board Skill 的 `ACCURACY_VERDICT=PASS` 日志，再采集：

```bash
python.exe <skill>/scripts/measure_latency.py \
  --execution-id <EXECUTION_ID> \
  --port COM6 --baudrate 115200 --ticks-per-us 24.0 \
  --window 50 --stable-tolerance 0.05 --timeout-seconds 110 \
  --accuracy-proof <absolute-path>/board_accuracy.log \
  --raw-log <absolute-path>/serial_raw.log \
  --output <absolute-path>/onboard_metric.json
```

Ctrl+C、超时、协议错误、非连续 seq 或未稳定窗口均返回非零，不生成 passing metric。输出目录会
自动创建，结果采用原子写入。采集完成后按 `workflow.md` 将 board、serial 和 metric 绑定到同一
manifest。

## 失败处理

| 场景 | 处理 |
|---|---|
| Host FAIL | 不构建性能 firmware，归档失败轮 |
| firmware FAIL | 保存构建日志，归档失败轮 |
| flash/accuracy FAIL | 不采 latency，归档失败轮 |
| 无有效 tick | 检查 marker、串口和时钟；最多重试两次 |
| seq 不连续或 ticks≤0 | 协议失败，不计算平均值 |
| latency 不低于 baseline | 完整归档为 `REJECTED`，再恢复本轮修改 |
| 同一设备错误连续两次 | 停止并请求用户处理 |

每轮必须保留 Host summary、firmware build、flash、board accuracy、原始串口、metric、fwpkg、
patch、生成代码 snapshot，以及 CPU/RISC-V archive 的 SHA256。
