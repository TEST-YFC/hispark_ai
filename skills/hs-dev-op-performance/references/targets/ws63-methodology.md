# WS63 算子性能优化方法

本文给出面向 WS63 的通用算子优化思路。它用于设计候选变量、解释板端结果和判断下一步，
不替代 `workflow.md` 的证据要求，也不保证某项技巧对所有算子有效。每个结论都必须在当前
算子、当前工具链和真实设备上重新验证。

## 1. 先建立当前平台画像

不要把其他 RISC-V 芯片或旧固件的经验直接套到当前设备。开始优化前至少确认：

- 编译器、优化等级、架构参数和可用 ISA 扩展；
- 通用寄存器、栈和代码尺寸约束；
- I-cache、D-cache 的容量、cache line 和启用状态；
- 输入、权重、临时 buffer 和输出位于 SRAM、Flash 还是映射区；
- 固件是否启用硬件预取、LTO 或其他全局优化；
- 编译器是否已经自动内联、向量化或展开热点循环。

不要预设 SIMD、Vector、cache 或预取能力存在。以当前 SDK 配置、编译选项、ELF 和反汇编
为准。优化目标不是减少 C 源码行数，而是减少板端实际发生的：

```text
无效计算 + 动态参数处理 + 内存流量 + 热点函数调用
+ spill/reload + I-cache miss + D-cache miss 延迟
```

## 2. 使用由高到低的优化漏斗

优先处理收益更稳定、解释更直接的变量：

```text
可信 baseline
  ↓
固定模型条件和通用路径冗余
  ↓
算法路径选择与无效计算消除
  ↓
静态参数暴露、常量折叠和专用 dispatch
  ↓
数据布局、循环顺序和内存流量
  ↓
热点调用、别名契约和编译器可见性
  ↓
寄存器、汇编、函数布局和 I-cache
  ↓
受控扫描对齐、D-cache 和预取
  ↓
判断 kernel 层或系统层是否到达天花板
```

没有完成前一层的分析时，不要直接堆循环展开、pragma 或预取。这些手段可能被寄存器压力、
代码体积和 cache 污染抵消。

## 3. 第一优先级：消除不需要的通用性

通用 kernel 往往覆盖多种布局、量化、zero point、bias、shape 和尾块。固定模型只使用其中
一部分。先从源模型、转换产物、生成代码和 kernel 参数中逐项建立证据：

| 已证明的静态条件 | 可调查的方向 |
|---|---|
| transpose 或布局固定 | 选择专用路径，删除运行期分支 |
| zero point 为固定值 | 删除可证明为零的补偿计算 |
| bias 不存在或恒为零 | 删除 bias 读取、加法和相关参数 |
| shift 为固定值 | 使用专用移位路径 |
| multiplier、shift 等数组完全相同 | 改成标量参数，允许立即数和常量折叠 |
| 参数只有少数连续分段 | 按分段调用专用路径 |
| shape 静态 | 固定 tile、尾块策略或小 shape 入口 |
| activation 范围固定 | 预计算 clamp 边界，删除重复转换 |

所有删除都需要数学、模型或数据契约证明。不能因为一组输入未触发某条路径，就把它当成
死代码。路径替换后还要检查生成代码确实调用了新路径，不能只看到源码存在。

## 4. 让编译器看见静态信息

### 4.1 标量化和分组静态参数

静态模型生成的数组不一定具有运行期动态性。先统计参数分布，再选择表示：

- 所有元素相同：使用标量；
- 只有少数连续分段：按取值分组调用；
- 每个 channel 都不同：保留数组路径；
- 参数由 case 决定：允许低成本、可验证的 shape-specific dispatch。

可检查 per-channel 算子的 multiplier、shift、zero point、clamp 和其他量化参数。标量化的
价值不只是少一次数组读取，还可能让编译器生成立即数指令、折叠分支和提前计算表达式。

### 4.2 只声明真实的别名契约

若输入、权重、输出和量化参数在调用期间确实不重叠，可考虑使用 `restrict`，减少编译器的
保守 reload，并允许更自由地调度 load/store。使用前必须沿调用链验证别名条件；错误契约
会产生未定义行为，不能把它当作试探性性能开关。

### 4.3 有选择地内联热点计算

适合评估内联的候选：

- 每个输出元素或每个小 tile 都调用的短函数；
- 参数中存在可折叠常量；
- 内联后能减少 call/ret 和寄存器保存；
- 展开后的函数仍足够小。

不应直接内联的候选：

- 把前处理、主 kernel 和后处理融合成一个大函数；
- 冷路径或只调用一次的复杂逻辑；
- 会显著延长寄存器活跃区间的代码。

减少调用与增大 I-cache 压力必须同时测量。

## 5. 围绕内存流量设计布局和循环

地址连续不等于访存已经最优。对每个热点循环画出：

```text
循环顺序 → 输入读取 → 权重读取 → accumulator 位置 → 输出写回
```

重点寻找：

- accumulator 在内层循环反复 load/store；
- 同一输入被不同输出位置或 channel 重复读取；
- 权重布局迫使跨 stride 访问；
- layout 转换本可在模型生成期一次完成，却在每次推理重复执行；
- 输出或临时 buffer 可以安全复用但尚未复用；
- tile 与真实 shape 不匹配，产生大量 scalar tail。

通用候选包括：

1. 交换循环顺序，让一个或少量 accumulator 常驻寄存器；
2. 离线重排常量权重，把转换成本移到模型生成阶段；
3. 按 shape 选择 tile，让主块覆盖更多维度并缩短尾循环；
4. 交织少量输出，一次输入 load 服务多个结果；
5. 对常见小工作集增加尺寸受控的专用路径。

数据布局修改必须同步检查权重生成、generated 调用代码、kernel 读取方式和 provenance；不能
只修改其中一层。

## 6. 循环展开和多累加器是高风险变量

机械展开不应被默认视为加速。开始实验前至少确认：

1. 反汇编显示编译器尚未自动展开；
2. 热点确实受循环控制或依赖链限制；
3. 估算新增 accumulator、指针和循环变量后的寄存器需求；
4. 栈帧和 spill/reload 没有明显增加；
5. 热函数尺寸没有跨越明显的 I-cache 风险点。

多个独立累加器有机会打断依赖链，但必须通过反汇编确认它们实际留在寄存器中。低展开因子
有效，不代表继续增加仍有效。每个展开因子都应作为独立变量归档。

## 7. 检查二进制布局和 I-cache

新增函数、调整函数大小、移动常量、改变 generated `Execute` 大小、内联或取消内联，都可能
改变热点代码布局。遇到“理论工作量下降但板端退化”时，比较：

```text
ELF/map/nm 中的函数地址与大小
热点反汇编
栈帧大小和寄存器保存
I-cache line/set 边界
相关只读数据和工作 buffer 地址
```

由偶然地址带来的提升只能算弱证据。可通过重复链接、改变邻近函数或运行更多 case 检查稳定
性；不要把一次布局红利解释为算法必然收益。

## 8. 区分对齐、cache 和预取

- 对齐主要处理访问边界及部分冲突；
- cache 容量和冲突决定工作集能否有效驻留；
- 预取尝试掩盖 miss 之后的数据取得延迟。

某一项无收益不能推出另外两项无收益。开始 cache 或预取实验前确认：

- D-cache 是否启用、容量和 cache line；
- 数据位于 SRAM、Flash 还是映射区；
- 工作集相对 cache 容量的大小；
- 访问步长、复用距离和冲突模式；
- 固件是否已经启用自动预取；
- 下级存储控制器是否另有预取机制。

预取通常是固件全局行为，不能直接改成仓库默认值。只有顺序访问、miss 延迟证据明确且用户
授权固件层实验时，才把预取深度作为单一变量，从关闭或较小深度开始扫描。深度越大不代表
越快；需要同时观察延迟掩盖、cache 污染以及对中断、协议栈、其他任务和其他算子的影响。

## 9. 用症状选择下一项实验

| 现象 | 优先调查 |
|---|---|
| baseline 极慢且通用分支多 | 算法路径和无效补偿计算 |
| per-channel 参数读取占热点 | 标量化、分组和常量折叠 |
| accumulator 反复访存 | 数据布局和循环交换 |
| 相同输入被重复读取 | 小规模输入复用或输出交织 |
| 小 case 退化、大 case 提升 | 固定开销、I-cache 和二进制布局 |
| 展开后退化 | 寄存器 spill、栈帧和代码体积 |
| C 代码已很紧但 CPI 仍高 | 指令依赖、cache miss 和 Flash 路径 |
| 对齐无效果 | 分别检查容量、冲突、延迟和预取 |
| 不同 shape 的最优参数不同 | shape-specific dispatch，不强求全局 tile |

如果没有性能计数器，可结合差分实验、ELF/map、反汇编、工作集估算和多 shape 趋势形成证据，
但要明确这是诊断推断，不是硬件计数器证明。

## 10. 保持单变量实验闭环

每个候选都遵循 `workflow.md`，并保持：

```text
固定源码、package、编译器、target 和设备参数
  → Host baseline
  → firmware、flash、板端正确性
  → latency baseline 归档
  → 修改一个变量
  → 刷新实际消费的 CPU/RISC-V archive
  → Host compare
  → firmware、flash、板端正确性、latency
  → accepted 或 rejected 归档
  → 回退 rejected 变量并重新刷新 package
```

一次实验至少记录：

- case、shape、mode 和 target；
- 源码 commit、dirty files 和唯一变量；
- CPU/RISC-V 编译器、build directory 和 archive hash；
- Host compare、firmware、flash、板端正确性各层状态；
- 原始串口、latency 样本、统计值和噪声范围；
- firmware/ELF hash、patch、日志及必要的反汇编；
- accepted/rejected 决策和回退状态。

Host PASS 不能证明 WS63 性能，firmware 构建成功也不能替代真实烧录和板端数据。

## 11. 用 case 矩阵约束过拟合

至少覆盖：

- 小工作集和大工作集；
- 单行/单位置与多行/多位置；
- 维度整除 tile 与存在 tail；
- 参数完全一致与 per-channel 参数混合；
- 工作集小于、接近和大于 D-cache；
- 商用模型中的真实 shape；
- 算子语义边界和不同量化范围。

对代表性 case 都提升的方案才适合进入通用 kernel。只对特定 shape 有效的方案，应采用明确、
低成本且可验证的 dispatch 条件，并保留其他 shape 的原路径。

## 12. 识别阶段性天花板

出现以下组合时，可判断当前 C kernel 接近阶段性天花板：

- 主计算占绝大多数动态指令；
- 编译器已完成有效的展开和指令选择；
- 寄存器接近占满，继续展开会 spill；
- 参数静态化、数据布局和主要内存流量已处理；
- 附属计算占比很低；
- 多轮单变量实验只产生噪声或稳定退化；
- 当前 cycles 已接近根据目标核估算的可达下界。

此时依次调查 generated 调用与 buffer 生命周期、链接布局、SRAM/Flash 放置、cache/预取、
编译器选项和 LTO。手写汇编或切换硬件后端会显著扩大范围，必须另行计划和授权。

## 13. 通用决策原则

1. 先消除不需要的通用性，再微调循环。
2. 优化动态执行，不以 C 代码行数判断收益。
3. 尽量把静态模型参数显式暴露给编译器。
4. 减少内存流量通常比减少索引计算更重要。
5. 数据布局、循环顺序和调用约定要联合设计。
6. 寄存器和 I-cache 是展开、融合的硬约束。
7. 小 case 与大 case 可能需要不同路径。
8. 对齐、cache 和预取是不同问题，不能互相替代结论。
9. kernel 天花板不等于系统天花板。
10. 只接受 Host 精度和真实板端数据共同支持的优化结论。
